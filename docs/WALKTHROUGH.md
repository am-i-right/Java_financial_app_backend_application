# Как устроен проект

## В каком порядке читать и разрабатывать

1. `Category`, `Money` — типы категорий и правила денег.
2. `Transaction`, `Income`, `Expense` — общие поля и наследование.
3. `Wallet` — коллекции, баланс, бюджеты; затем `WalletTest`.
4. `User`, `AuthService` — регистрация, пароль, активная сессия.
5. `FinanceManager` — выбор кошелька текущего пользователя; затем тест изоляции двух аккаунтов.
6. `Report`, `ReportGenerator` — интерфейс и текстовое представление данных.
7. `Main` — связывает готовые сервисы с консолью; затем `MainTest`.
8. `pom.xml`, `.github/workflows/ci.yml` — воспроизводимая сборка и автоматические тесты.

После каждого шага можно запускать `mvn test`. Модели и сервисы не зависят
от консольного меню: в дальнейшем к ним можно подключить другой интерфейс.

## Почему BigDecimal

`double` хранит двоичные дроби, поэтому десятичные суммы могут представляться
приближённо. `BigDecimal` из строки сохраняет точное значение:

```java
BigDecimal amount = new BigDecimal("120.50");
```

Не создавайте денежные значения через `new BigDecimal(0.1)`.
`Money.positive()` проверяет положительность и приводит сумму к двум знакам
через `RoundingMode.UNNECESSARY`. Значение `1.001` вызовет понятную ошибку,
вместо скрытого округления до `1.00`. Для сравнения величин используется
`compareTo()`, поскольку `BigDecimal.equals()` учитывает также масштаб.

## Как вычисляется баланс

`Income.getSignedAmount()` возвращает положительную сумму, `Expense` — отрицательную.
`Wallet.getBalance()` складывает результаты. Общая логика не знает, с каким
подклассом работает: это полиморфизм.

Отдельное поле `balance` пришлось бы обновлять при каждом изменении истории.
В учебном проекте проще пересчитать баланс за O(n), где n — число операций.
Списки небольшие, а риск рассинхронизации исчезает.

## Как связаны пользователь, категория и кошелёк

У каждого `User` свой объект `Wallet`. `AuthService` хранит пользователей в
`Map<String, User>` и ссылку на текущего пользователя. Каждый публичный финансовый
метод `FinanceManager` сначала получает кошелёк через `auth.getCurrentUser()`.
Если вход не выполнен, операция завершается исключением до изменения данных.

Внутри кошелька названия категорий приводятся к нижнему регистру через `Locale.ROOT`
и обрезаются по краям. При этом отображаемое название сохраняет регистр.
`LinkedHashMap` обеспечивает понятный порядок вывода — порядок создания.

В `Wallet.addTransaction()` проверяется принадлежность объекта категории кошельку.
Категория «Еда» другого пользователя — другой объект, даже если название совпало.
`Category` намеренно не переопределяет `equals()`/`hashCode()`: здесь значима
идентичность конкретной категории. `Income` и `Expense` дополнительно проверяют её тип.

Проверка владения нужна и на уровне модели, чтобы прямое использование `Wallet`
в тесте или другом интерфейсе не позволяло случайно смешать категории разных кошельков.

## Как считается месячный бюджет

Хранилище лимитов имеет тип:

```java
Map<YearMonth, Map<Category, BigDecimal>> budgets;
```

Первый ключ — календарный месяц с годом, второй — категория расходов.
Это позволяет независимо установить лимиты на декабрь 2026 и январь 2027.

При установке лимита сначала проверяются все аргументы, затем изменяется коллекция.
Выражение `computeIfAbsent(month, ...)` создаёт внутреннюю карту только при первом
бюджете этого месяца. `put(category, limit)` создаёт или заменяет один лимит.

При расчёте статуса бюджетной категории цикл выбирает только расходы, у которых:

1. категория совпадает с категорией лимита;
2. `YearMonth.from(transaction.getDate())` совпадает с месяцем бюджета.

Остаток равен `limit - spent`. Он может быть отрицательным. Превышение —
строго `spent.compareTo(limit) > 0`; равенство не вызывает предупреждения.
Транзакции не удаляются и не блокируются при превышении.

Расчёт всех статусов занимает O(b × n), где b — количество бюджетов в выбранном
месяце, n — число операций. Для учебного проекта обычные циклы проще отдельного
кеша или индексов. `BudgetStatus` — неизменяемый снимок результата расчёта.

## Inner и static nested классы

`Wallet.Alert` — нестатический внутренний класс. Его экземпляр связан с конкретным
кошельком и может вызвать `getBalance()` и `getBudgetStatuses()` внешнего объекта.
Он возвращает сообщения, а не вызывает `System.out.println()`: вывод остаётся в `Main`.
Проверять нужно расходы относительно лимита категории. Сравнение общего баланса
с лимитом категории дало бы неправильный результат.

`Transaction.DateComparator` — статический вложенный класс. Он сравнивает две
переданные операции, не нуждается в конкретном внешнем объекте и создаётся так:

```java
new Transaction.DateComparator();
```

`Wallet.BudgetStatus` — вложенный `record`, который неявно является статическим.
Его аксессоры называются `limit()`, `spent()`, а не `getLimit()` и `getSpent()`.

Анонимный класс в сортировке по сумме создаёт реализацию `Comparator` прямо
в месте использования. Это демонстрация синтаксиса; отдельный файл для него не нужен.

## Зачем интерфейс Report

`FinanceManager.generateReport()` принимает `Report`, а не конкретный генератор.
Текстовая реализация находится в `ReportGenerator`. Тест подставляет короткую
лямбду, которая тоже реализует этот интерфейс. Так демонстрируется зависимость
от контракта без фабрик, контейнера зависимостей или системы плагинов.

Отчёт суммирует только операции выбранного месяца. Общий баланс подписан отдельно,
чтобы его не перепутали с разницей доходов и расходов месяца.

## Как защищён пароль

У каждого пользователя случайная соль длиной 16 байт. Стандартный Java API
`SecretKeyFactory` вычисляет PBKDF2-HMAC-SHA256 с 210 000 итераций и результатом 256 бит.
При входе ввод проходит то же преобразование с сохранённой солью, результаты
сравниваются через `MessageDigest.isEqual()`. Параметры хеширования сосредоточены
в `User`, алгоритм самостоятельно не реализуется.

Соль и хеш — закрытые поля без геттеров. Временный `PBEKeySpec` очищается
в `finally`. Для простоты меню использует `Scanner` и строки: введённый пароль
виден, а полное стирание строк из памяти не гарантируется. Это ограничение
учебной консоли, а не готовая система авторизации веб-сервиса.

## Ошибки и целостность данных

Модели отклоняют неверные аргументы через `IllegalArgumentException`, сервис
авторизации — отсутствие сессии через `IllegalStateException`. `Main` перехватывает
эти ожидаемые ошибки и возвращает пользователя в меню. Форматы дат и чисел
получают отдельные сообщения. Неожиданные программные ошибки не скрываются
общим `catch (Exception)`.

Для ввода используется один `Scanner` и только `nextLine()`. Смешивание `nextInt()`
с `nextLine()` потребовало бы дополнительно обрабатывать оставшийся перевод строки.
EOF обрабатывается отдельным внутренним исключением `EndOfInput`, которое завершает цикл.

`List.copyOf()` возвращает неизменяемый снимок. Внешний код не может очистить
историю или удалить категорию через геттер; ранее полученный снимок также
не меняется при следующей операции. Сами категории и операции неизменяемы.

## Что сознательно оставлено простым

- Нет generic-репозиториев: достаточно коллекций в `AuthService` и `Wallet`.
- Нет отдельной сущности бюджета: для лимита хватает карты и `BudgetStatus` для вывода.
- Нет фонового планировщика: месяц определяет дата операции.
- Нет пользовательских исключений для каждого вида ошибки: стандартных достаточно.
- Нет кеша баланса, событий, фабрик, DTO для каждого класса и контейнера DI.
- Нет сохранения на диск: это соответствует требованию хранения данных в памяти.

Для проверки вручную пройдите сценарий из README, затем повторите расход
с суммой ровно в лимит, с неверным типом категории и из аккаунта второго
пользователя. Автоматические версии этих сценариев находятся в `src/test/java`.
